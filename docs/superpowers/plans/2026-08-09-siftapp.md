# SwiftUI App Implementation Plan (Native Sift, Plan 4 of 5)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace `web/index.html` and `shell/**` with a native SwiftUI window — sources sidebar, `NSTableView` grid, column inspector, filter toolbar, SQL console, and every sheet — driven directly by the `SiftEngine` actor. At the end of this plan Sift is a Mac app with no WKWebView, no loopback server, and no JavaScript.

**Architecture:** Two new targets. **`SiftUI` is a library** holding every view, every view model and every decision; **`SiftApp` is an `executableTarget`** holding `@main`, the menu bar, the toolbar and LaunchServices document handling, and nothing else. That split is not taste — a SwiftPM test target cannot import an `executableTarget`, so anything that lands in `SiftApp` is permanently untestable. `Tests/SiftUITests` covers `SiftUI`.

**Tech Stack:** Swift 6, SwiftPM, swift-testing, SwiftUI, AppKit, `SiftEngine`, `SiftCore`, `DuckDBKit`.

**Spec:** `docs/superpowers/specs/2026-08-09-native-sift-design.md` §4, §7, §9, §10, §11, §13a, §14.

**Plan sequence:** 1 DuckDBKit ✅ → 2 SiftCore ✅ → 3 SiftEngine + CLI ✅ → **4 Grid + panels (this)** → 5 Bundle and delete.

## Global Constraints

- Swift tools version **6.0**. Platform floor **macOS 14**. Zero third-party dependencies. Pure SwiftPM — no Xcode project, ever.
- `SiftUI` and `SiftApp` may import `SiftEngine`, `SiftCore`, `DuckDBKit`, SwiftUI and AppKit. **`SiftCore` stays Foundation-only** — never add an import to it.
- **`SiftApp` is an `executableTarget`, so no test can import it.** `main.swift`, `AppDelegate.swift` and the menu/toolbar builders live there; every decision, every transformation and every piece of state lives in `SiftUI`. If you find yourself wanting to test something in `SiftApp`, it is in the wrong target — move it down.
- **No `NumberFormatter` / `DateFormatter` / `ISO8601DateFormatter` / `Text(_, format: .number)` / `.formatted()` for anything a user or a test sees.** They follow `Locale.current`. Three bugs of exactly this shape have already shipped on this branch. Hand-roll it; `Cell.display` and the ported `groupDigits` below are locale-independent by construction.
- **This Mac has only the macOS 26 SDK, so it is a bad oracle.** Code that compiles here can fail for everyone else. CI on `macos-15` is the only real check. Prefer APIs available on the macOS 14 floor — see "Newer APIs that must not be used" below.
- Every commit leaves `swift build && swift test` green and **warning-free**, including the existing DuckDBKit / SiftCore / SiftEngine suites. Suites run **in parallel**; do not introduce anything needing `.serialized`.
- **Any script committed here needs `git add --chmod=+x`** — this repo has `core.fileMode=false` (its `.git` is on an SMB share), so a plain `chmod +x` records mode `100644` and CI dies on a fresh clone. Verify with `git ls-files -s <path>` showing `100755`.
- Commit as the repo's configured identity. **Never `git reset`, `git checkout --`, or `git stash`** on this branch — a concurrent session shares the underlying repository.
- Do not touch `engine/`, `web/`, `shell/`, `dev.sh`, `bin/sift-open`, `requirements*.txt`, `pytest.ini`, or the legacy files at the repo root. They are deleted in Plan 5, not before.
- **Edits to `SiftEngine` are permitted only where a task names them.** Three tasks do (Task 2's open-home guard, Task 5's sort cap, Task 12's staging-policy accessors), and each says exactly what it adds. Nothing else in `Sources/SiftEngine/**`, and nothing at all in `Sources/SiftCore/**` or `Sources/DuckDBKit/**`.

## Concurrency model — decided here, not per task

`Session` is an `actor` and **every read is an `await`**. The view layer's rule, in four facts:

1. **`AppState` and every view model are `@MainActor @Observable` classes.** SwiftUI observes them directly. They are the only mutable UI state.
2. **Everything that crosses the boundary is already `Sendable`** — `Table`, `TablePage`, `Cell`, `SessionState`, `EngineInfo`, `ColumnProfile`, `DistinctPanel`, `HistogramPanel`, `BadRowsPanel`, `StagedSource`, `LengthBucket`. No new bridging type is needed and none may be added. `Connection` and `ResultSet` never leave `SiftEngine`.
3. **Scrolling never spawns a task per block.** One `PageLoader` per open table runs a single-flight pump: it holds a *set* of wanted block indices, fetches the one nearest the viewport centre, delivers it, and repeats. Scrolling past a block removes it from the set before it is ever requested. This is the native equivalent of the web grid's `AbortController` map (`web/index.html:809-868`), and it is strictly better here — see the landmine below for why per-block `Task.cancel()` would not have worked.
4. **The engine is polled, not subscribed.** SSE is gone and `Session` has no change channel. `AppState` calls `await session.state()` on an adaptive cadence: **250 ms** while anything is in flight (`counting`, `staging != nil`, `profiling`), **2 s** otherwise, plus an immediate refresh after every user action. Considered and rejected: adding an `AsyncStream` to `Session`. It is a real engine change that does not fix the one thing that actually stalls the UI (the actor blocking inside `page`, fact 3 of `Session.swift`'s header), and `state()` is a snapshot of a handful of structs.

## 🔴 Landmines — read before writing any code

**`Task.cancel()` does not cancel an actor call.** `await session.page(...)` runs to completion on the actor whether or not the calling `Task` was cancelled; `Session.page` never checks `Task.isCancelled` and never suspends. Cancelling a per-block task therefore only **discards** the result — the work still happens, still queues on the actor, and still delays the block the user is actually looking at. That is why Task 4 is a single-flight pump with a mutable want-set rather than a task per block. Say "discarded", never "cancelled", in comments.

**A public struct's memberwise initializer is `internal`.** `TablePage`, `TablePage.ColumnInfo`, `DistinctPanel`, `DistinctPanel.Value`, `HistogramPanel`, `HistogramPanel.Bucket`, `BadRowsPanel`, `LengthBucket`, `StagedSource`, `PurgeResult`, `EngineInfo` and `SessionState` all declare `public let` fields and **no `public init`** — so `SiftUI` and `Tests/SiftUITests` can read them but **cannot construct them**. Consequences, both load-bearing:
- The view models must use **`SiftCore.Column`** (which does have `public init(name:type:)`) as their column type, converting with `Column(name: info.name, type: info.type)`. `Column.init` recomputes `kind` through the same `kind(of:)` the engine used, so the value is identical.
- Any test that needs a `TablePage`, a `DistinctPanel` or a `HistogramPanel` must get it from a **real `Session` over a real fixture**. Do not add `public init`s to the engine to make a test easier. `PageLoader` is generic (Task 4) precisely so its own tests can use a payload they *can* build.

Types that **are** constructible, and which tests should use freely: `Cell`, `Column`, `Table`, `SourceSpec`, `SourceKey`, `QuerySpec`, `QuerySpec.SortTerm`, `Filter`, `SQLValue`, `ColumnProfile`, `StageDecision`, `StagingProgress`, `SheetInfo`, `RowEstimate`.

**`Cell.display` is lossy on purpose** (its own doc comment says so): it renders `.null` and `.text("")` identically as `""`, collapsing two of the three states — NULL, `''`, `'N/A'` — that spec §9 calls non-negotiable. The grid **must** switch on the `Cell` case for that distinction and use `display` only for the glyph. Never `String(describing:)` a `Cell`.

**`Cell.decimal` carries its scale** — `case decimal(Decimal, scale: Int)`. `Cell.display` already re-pads it, so a `DECIMAL(10,2)` renders `10.50`. Do not re-format a decimal in the view layer; you will get `10.5`.

**`Cell.list([Cell])` exists and every `switch` over `Cell` must handle it.** The bad-rows sheet matches on `.list` directly to get the failing column names — it must not re-split `display`'s joined text.

**Non-`async` actor methods still need `await`.** `setSpec`, `exitSQLMode`, `renderedSQL`, `snippet`, `stageNow`, `cancel`, `stagedEntries`, `purgeStaged` and `table(_:)` are declared `throws` (or plain) rather than `async`, but every call from outside the actor is still `try await session.setSpec(...)`. `engineInfo()`, `stagedTotalBytes()`, `relation(_:)` and `dropPrivateStore()` are `nonisolated` and need no `await`.

**Newer APIs that must not be used** — tempting, and all above the macOS 14 floor. This Mac will compile them; `macos-15` will not:
- `onGeometryChange(for:of:action:)` (macOS 15) — use `GeometryReader`.
- `@Entry` for `EnvironmentValues` (macOS 15) — write the `EnvironmentKey` by hand, or pass the value down explicitly.
- `TabView(role:)` / the `Tab` type (macOS 15) — the inspector's three tabs are a `Picker` with `.pickerStyle(.segmented)`.
- `MeshGradient`, `.symbolEffect(.wiggle)`, `.scrollBounceBehavior` refinements, `WindowDragGesture` (macOS 15), anything Liquid Glass (`.glassEffect`, `.buttonStyle(.glass)`, macOS 26).
- `Table`/`TableColumnForEach` from SwiftUI — available, but wrong: it needs a `RandomAccessCollection` of *every* row. Spec §9 forbids it.

Safe and used: `NavigationSplitView` + `NavigationSplitViewVisibility`, `.inspector(isPresented:)`, `@Observable`, `ImageRenderer`, `.contextMenu`, `.searchable` is **not** used (the value search is a plain `TextField`, matching `web/index.html:1235`).

```swift
import DuckDBKit
import Foundation
import Observation
import SiftCore
import SiftEngine

@MainActor
@Observable
public final class AppState {
    public let session: Session
    public let engine: EngineInfo

    /// Mirror of the actor's catalog, refreshed by `poll()`. Read-only for views.
    public private(set) var tables: [Table] = []
    public var activeName: String?
    /// One user-facing sentence, or nil. Python emitted `{"type": "error"}`; there is no SSE, so
    /// the banner IS the notification.
    public var banner: String?

    private var models: [String: TableViewModel] = [:]
    private var pollTask: Task<Void, Never>?

    public init(session: Session) {
        self.session = session
        self.engine = session.engineInfo()   // nonisolated
    }

    public var active: Table? { tables.first { $0.name == activeName } }

    public func open(path: String, sheet: String? = nil) async {
        do {
            let t = try await session.openPath(path, sheet: sheet)
            await refresh()
            activeName = t.name
        } catch {
            banner = error.localizedDescription
        }
    }

    public func close(_ name: String) async {
        do { try await session.closeTable(name) } catch { banner = error.localizedDescription }
        models[name] = nil
        await refresh()
        if activeName == name { activeName = tables.first?.name }
    }

    public func refresh() async {
        let snapshot = await session.state()
        tables = snapshot.tables.sorted { $0.openedAt < $1.openedAt }
        if let activeName, !tables.contains(where: { $0.name == activeName }) {
            self.activeName = tables.first?.name
        }
        for t in tables { models[t.name]?.apply(t) }
    }

    /// One view model per open table, created lazily and kept so the page cache survives a tab
    /// switch — the web build cleared its blocks on every switch and re-fetched (`resetGrid`).
    public func model(for name: String) -> TableViewModel? {
        guard let t = tables.first(where: { $0.name == name }) else { return nil }
        if let existing = models[name] { return existing }
        let m = TableViewModel(session: session, table: t)
        models[name] = m
        return m
    }

    /// Adaptive polling replaces SSE. 250 ms while the engine is doing something the user is
    /// waiting on, 2 s otherwise. Every user action calls `refresh()` directly as well, so this
    /// only has to catch *background* progress: the exact count, bad-row detection, the profile,
    /// and a staging job.
    public func startPolling() {
        pollTask?.cancel()
        pollTask = Task { [weak self] in
            while !Task.isCancelled {
                guard let self else { return }
                await self.refresh()
                let busy = self.tables.contains {
                    $0.counting || $0.staging != nil || $0.profiling
                }
                try? await Task.sleep(nanoseconds: busy ? 250_000_000 : 2_000_000_000)
            }
        }
    }

    public func stopPolling() { pollTask?.cancel(); pollTask = nil }
}
```

/// A CSV with a numeric, a text and a deliberately three-state column: a real NULL (missing
/// field), a real empty string, and the literal sentinel "N/A". Those three staying distinct is
/// the product's whole premise (spec §9), and every rendering test needs a row of each.
@discardableResult
func makeCSV(in dir: URL, name: String = "t.csv", rows: Int = 12) throws -> String {
    var out = "id,label,note\n"
    for i in 0..<rows {
        let note = i % 3 == 0 ? "" : (i % 3 == 1 ? "\"\"" : "N/A")
        out += "\(i),row\(i),\(note)\n"
    }
    let path = dir.appendingPathComponent(name).path
    try out.write(toFile: path, atomically: true, encoding: .utf8)
    return path
}

- [ ] **Step 3: Write `OpenHomes.swift`**

```swift
import Foundation

/// Process-wide set of `SIFT_HOME` paths a live `Session` is holding.
///
/// Spec §13a: two `Database` handles on one file *in one process* are two independent DuckDB
/// instances that cannot see each other's catalog, so the second one's flush silently overwrites
/// the first one's. That is not a lock contention problem — measured, there is no lock error
/// in-process at all, which is precisely why `Session`'s `sharedStore` fallback never fires for
/// it and reports `true` for both. The only thing that can stop it is refusing the second open.
///
/// `@unchecked Sendable` with an explicit lock rather than an actor: `Session.init` is a
/// synchronous throwing initializer and cannot `await`.
final class OpenHomes: @unchecked Sendable {
    private let lock = NSLock()
    private var paths: Set<String> = []

    /// `true` if this call took ownership; `false` if someone else already has it.
    func claim(_ path: String) -> Bool {
        lock.withLock { paths.insert(path).inserted }
    }

    /// Idempotent on purpose — `shutdown()` and `deinit` both call it, and a `Session` that is
    /// shut down and then deallocated must not release a claim a *later* session has taken.
    /// Releasing a path this instance no longer owns is impossible because the claim is by path
    /// and a path is only ever held by one instance at a time.
    func release(_ path: String) {
        lock.withLock { _ = paths.remove(path) }
    }
}
```

`PageLoader` shape:

```swift
@MainActor
public final class PageLoader<Payload: Sendable> {
    public typealias Fetch = @Sendable (Int) async throws -> Payload

    public var onDeliver: ((Int, Payload) -> Void)?
    public var onFailure: ((Error) -> Void)?
    /// Bumped by `invalidate()`. A delivery whose generation no longer matches is dropped: the
    /// filter, sort, staged-ness or table changed while it was in flight, so it describes rows
    /// that are no longer what the grid is showing.
    public private(set) var generation = 0

    private let fetch: Fetch
    private var wanted: [Int] = []
    private var centre: Double = 0
    private var pump: Task<Void, Never>?

    public init(fetch: @escaping Fetch) { self.fetch = fetch }

    /// Replace the want-set. Nearest-to-`centre` wins, so the rows actually on screen are
    /// fetched before the overscan around them.
    public func request(blocks: [Int], centre: Double) {
        self.centre = centre
        for b in blocks where !wanted.contains(b) { wanted.append(b) }
        wanted.removeAll { !blocks.contains($0) }
        startPumpIfIdle()
    }

    public func invalidate() {
        generation += 1
        wanted.removeAll()
    }

    private func startPumpIfIdle() {
        guard pump == nil else { return }
        pump = Task { [weak self] in
            while let self, let block = self.takeNearest() {
                let stamp = self.generation
                do {
                    let payload = try await self.fetch(block)
                    // Not "cancelled" — `Task.cancel()` does not stop an actor call, so the work
                    // has already happened. This only stops it being shown for a spec that is no
                    // longer on screen.
                    if stamp == self.generation { self.onDeliver?(block, payload) }
                } catch {
                    if stamp == self.generation { self.onFailure?(error) }
                }
            }
            self?.pump = nil
        }
    }

    /// The wanted block closest to the viewport centre, removed from the set. Nearest-first is
    /// what keeps the rows under the cursor from queueing behind overscan.
    private func takeNearest() -> Int? {
        guard let best = wanted.min(by: {
            abs(Double($0) - centre) < abs(Double($1) - centre)
        }) else { return nil }
        wanted.removeAll { $0 == best }
        return best
    }

    /// Test seam: awaits the pump so a test can assert on what was fetched. `internal`, reached
    /// through `@testable import` — it exists for the suite and has no place in the app.
    func drainForTest() async { await pump?.value }
}
```

A thrown error goes to `onFailure` and the pump continues to the next block — one bad page must not wedge the grid.

### Task 5: `TableViewModel`, and the 5,000,000-row sorted-truncation fix (spec §13a)

**Files:** Create `Sources/SiftUI/TableViewModel.swift`, `Tests/SiftUITests/TableViewModelTests.swift`, `Tests/SiftEngineTests/SortCapTests.swift`. Modify `Sources/SiftEngine/Session.swift`, `Sources/SiftEngine/Table.swift`. Delete the Task 1 stub.

- Produces:
  - `SiftEngine`: `public let sortMaterializeMax = 5_000_000` (widened from internal), `Table.scrollableRows: Int?`, `Table.sortTruncated: Bool`.
  - `SiftUI`: `@MainActor @Observable public final class TableViewModel` with `let name: String`, `private(set) var table: Table`, `columns: [Column]`, `scrollExtent: Int`, `rowSlot(at:) -> RowSlot`, `ensureVisible(firstRow:rowsOnScreen:)`, `setSort(_:) async`, `setFilters(_:) async`, `loadFirstPage() async throws`, `apply(_ table: Table)`, `profile: [ColumnProfile]`, and `public enum RowSlot: Equatable { case loaded([Cell]); case pending }` (`Equatable` because the grid tests compare against `.pending`, and `Cell` is already `Equatable`).

**The §13a gap, and the call.** `Session.sortedRelation` always materializes and materializes at most `sortMaterializeMax` (5,000,000) rows. Pages past that return **empty** while `visibleRows` still reports the full count — so a sorted 100M-row table sizes its scroll extent for 100M and 95M of them come back blank. Spec §13a names two fixes.

**Take option one: cap the reported extent, and say so on screen.** Reasons, in order:
1. Re-materializing a window as the user scrolls reintroduces exactly the bug materialize-once exists to prevent. `sortedRelation`'s own doc comment records the measurement: re-sorting the same static, tie-bearing table at different `LIMIT`/`OFFSET` pairs does **not** reproduce the same tie order — 4 rows out of 1000 landed on two pages and 4 on none. Two separately materialized windows have that same seam, and a duplicated-or-dropped row in a tool whose premise is not lying about data is worse than a missing tail.
2. Making windowing correct needs a total order — appending every column as a tiebreak — which changes what the user asked to sort by, and still pays a full sort per window.
3. Capping makes the scroll extent *true*: everything the thumb can reach returns rows. The tail is not silently missing, it is named in a banner with the way to reach it (clear the sort).

Deliberately not raising `sortMaterializeMax`: it is Python's number, ported verbatim, and 5M rows of materialized copy is already the memory ceiling the engine chose.

**The §13a paging cliff, and what the UI shows.** `Session.page` runs synchronously on the actor and never suspends, so the first sorted page over a large table blocks **every other actor call** for as long as the materialization takes — `table`, `state`, a second `openPath`, and every background callback all wait. `Session.page`'s own doc comment records this as a deliberate, un-fixed cliff and says the grid must show a busy state across it.

The answer, in three layers:
1. **Every unloaded row is already a skeleton** (Task 6). That covers the ordinary sub-second case with no extra machinery.
2. **`BusyState` flips visible after 400 ms.** `PageLoader` calls `busy.begin("Loading rows…")` before the `await` and `busy.end()` after; `begin` schedules a `Task` that sleeps 400 ms and then sets `visible = true` unless `end()` already ran. **This works only because `BusyState` is on the `MainActor`, which is not the actor that is blocked** — a flag the blocked actor had to set would arrive after the stall it was meant to announce. Say that in the comment.
3. **Sorting a large table shows the overlay immediately**, without the 400 ms wait: `TableViewModel.setSort` calls `busy.begin("Sorting <grouped n> rows…")` when `table.visibleRows ?? 0 > 250_000`, because that is the case where the wait is *known* in advance rather than discovered.

The overlay is a centred `ProgressView` (indeterminate — the engine reports no progress for a sort) plus the message, over a translucent scrim on the grid only, leaving the sidebar and menu bar live.
