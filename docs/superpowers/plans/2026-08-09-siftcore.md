# SiftCore Implementation Plan (Native Sift, Plan 2 of 5)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Port `engine/core/**` — 1,783 lines of deliberately pure Python — to Swift, preserving its 128 tests as the behavioural contract, so that identifier quoting, SQL generation, the SELECT-only gate, format detection, profiling, staging policy and copy-as-code all work identically with no Python at runtime.

**Architecture:** One library target, `SiftCore`, depending on **Foundation only**. Its test target depends on `DuckDBKit` (Plan 1) because a handful of tests genuinely need a connection — but the library itself never does. That constraint is why 216 of the Python suite's 218 tests run in under 10 ms each, and it is the single most valuable property to carry across.

**Tech Stack:** Swift 6, SwiftPM, swift-testing, Foundation. `DuckDBKit` in the test target only.

**Spec:** `docs/superpowers/specs/2026-08-09-native-sift-design.md` §4, §7, §11.

**Plan sequence:** 1 DuckDBKit ✅ → **2 SiftCore (this)** → 3 SiftEngine + CLI verifier → 4 Grid + panels → 5 Bundle and delete.

## The porting rule — read this before any task

`engine/tests/**` is the spec, and `AGENTS.md` says it is read-only: never weaken a test to make a change pass. Porting is technically rewriting, so:

> **Each Swift test keeps its Python original's assertion values verbatim.** Not "equivalent" — the same strings, the same numbers. If a Python test asserts `'"region" IN (?, ?)'`, the Swift test asserts exactly that string. The Python file stays in the tree until its Swift counterpart asserts the same thing; it is deleted only in Plan 5.

Where a Python test asserts on something Swift cannot express identically, **do not silently adapt it** — report it, and it gets an explicit decision. This plan deliberately does **not** re-transcribe the 1,614 lines of Python tests into task briefs. Every defect in Plan 1 came from the plan mis-transcribing something; pointing at the original removes that failure mode entirely. Read the Python file, port it.

## Global Constraints

- Swift tools version **6.0**. Platform floor **macOS 14**. Zero third-party dependencies.
- **`SiftCore` imports Foundation and nothing else.** No `DuckDBKit`, no `CDuckDB`. A function needing a connection does not belong in this module — it goes to `SiftEngine` in Plan 3. This is checked by the compiler and is load-bearing.
- `Tests/SiftCoreTests` may import `DuckDBKit`.
- **Never use `NumberFormatter`, `DateFormatter`, or `ISO8601DateFormatter` for any value that reaches a user or a test assertion.** They follow `Locale.current` and `Calendar`. Plan 1 shipped two bugs this way — a blob size that rendered four different ways by region, and a date shifted 9-10 days before 1582. Hand-roll it; the Python originals are all locale-independent.
- Commit as the repo's configured identity. Do not override `user.name`/`user.email`.
- **Any script committed here needs `git add --chmod=+x`** — `core.fileMode=false` (the `.git` is on an SMB share) silently discards the executable bit and a fresh clone breaks CI.
- **Never `git reset`** on this branch; a concurrent session shares the underlying repository.
- Every commit leaves `swift build && swift test` green and warning-free, including Plan 1's 53 tests.
- Do not touch `engine/`, `web/`, `shell/`, `build-app.sh`, `dev.sh`, `Sift.app`, `requirements*.txt`, `pytest.ini`, `.github/workflows/ci.yml`, or anything under `Sources/DuckDBKit` and `Sources/CDuckDB`.

### Task 2: Ident

**Ports:** `engine/core/ident.py` (67 lines) and `engine/tests/test_ident.py` (7 test functions).

**Files:** Create `Sources/SiftCore/Ident.swift`, `Tests/SiftCoreTests/IdentTests.swift`.

**Gotchas:**
- **The rule this module exists to enforce: identifiers are quoted, values are parameterized.** `q` doubles embedded `"`, `qlit` doubles embedded `'`. Both are one line and both are security-critical.

Swift: `decomposedStringWithCompatibilityMapping` (NFKD — note *compatibility*, not canonical), then filter out characters in the combining-marks range, then keep only ASCII. `"Ünïcode"` must become `unicode`, not vanish. The Python test pins this.
- A leading digit gets a `t_` prefix, because an unquoted identifier cannot start with one and the copy-as-pandas snippets show unquoted names.
- Name cap is 60 characters, trailing `_` stripped after truncation, then collision suffixes `_2`… up to 1000.

### Task 3: SQLGen — filters, paging, render, and the wrap

**Ports:** the filter/paging/render half of `engine/core/sqlgen.py`, and the matching tests in `engine/tests/test_sqlgen.py`.

**Files:** Create `Sources/SiftCore/SQLGen.swift`, `Tests/SiftCoreTests/SQLGenTests.swift`.

**Interfaces produced:**
- `func whereClause(_ filters: [Filter], _ cols: [String: Column]) throws -> (String, [SQLValue])`
- `func orderBy(_ sort: [(String, String)], _ cols: [String: Column]) throws -> String`
- `func pageSQL(_:cols:rel:limit:offset:) throws -> (String, [SQLValue])`
- `func countSQL(_:cols:rel:) throws -> (String, [SQLValue])`
- `func renderSQL(_:cols:) -> String`
- `func wrapUserSQL(_ sql: String, limit: Int, offset: Int) -> (String, [SQLValue])`
- `struct UnknownColumn: Error` — carries the column name

**Bound parameters: `SiftCore` declares its own type.** `DBValue` lives in `DuckDBKit`, which `SiftCore` cannot import — and `DuckDBKit` must not import `SiftCore` either, since it is a standalone DuckDB wrapper that knows nothing about Sift. So `SiftCore` declares:

```swift
/// A bound query parameter. Mirrors DuckDBKit's `DBValue` case-for-case, and is a
/// separate type on purpose: SiftCore imports Foundation only, and DuckDBKit is a
/// standalone wrapper that must not learn about Sift. SiftEngine imports both and
/// maps between them in one switch.
public enum SQLValue: Sendable, Equatable {
    case null
    case bool(Bool)
    case int(Int64)
    case double(Double)
    case text(String)
}
```

Plan 3 owns the five-line `SQLValue → DBValue` mapping. Do not add a dependency in either direction to avoid writing it.

**Gotchas:**
- **The invariant, pinned by the tests: identifiers via `q()`, values always bound as `?`.** `test_a_hostile_column_name_stays_one_quoted_identifier` asserts the exact string `'"""; DROP TABLE x; --" = ?'` and then runs it against a real connection. Port both halves.
- **`in`/`not_in` split NULL out.** `col IN (NULL)` never matches and `col NOT IN (NULL)` is never true, and the distinct panel makes NULL clickable, so this is normal use rather than an edge case. The exact expected strings are in the Python tests — including that `not_in` without NULL still keeps NULL rows: `("region" NOT IN (?) OR "region" IS NULL)`.
- **`wrapUserSQL`'s newlines are load-bearing, not cosmetic.** The flat form `SELECT * FROM ( <sql> ) AS _q` lets a trailing `-- comment` swallow the closing paren and rejects a legitimate query. Measured on 1.5.5, and `test_wrap_puts_the_closing_paren_on_its_own_line` pins it against a live connection. That test needs `DuckDBKit`.
- `renderSQL` inlines values **only** because it is display text for the SQL box and clipboard, never executed. Keep that comment; the executed path is `pageSQL` with bound parameters.
- `renderSQL`'s literal rendering must match Python's: `None`→`NULL`, bools→`TRUE`/`FALSE`, numbers via `repr`, strings single-quoted with `''` doubling.
- `orderBy` emits explicit `NULLS LAST` so ordering survives engine-default changes.

### Task 4: SQLGen — panels, profiling and bad rows

**Ports:** the remaining half of `engine/core/sqlgen.py` (lines 134-306) and its tests.

**Files:** Create `Sources/SiftCore/SQLGenPanels.swift`, `Tests/SiftCoreTests/SQLGenPanelsTests.swift`.

**Interfaces produced:** `topNSQL`, `distinctStatsSQL`, `histogramSQL`, `profileExtraSQL`, `uncastableSQL`, `badRowCountSQL`, `badRowsSQL`, and `safeType(_:) throws -> String`.

**Gotchas:**
- **`profileExtraSQL` and `uncastableSQL` alias by index (`c0__empty`), never by name** — two columns whose names sanitize identically must not collide. A Python test pins exactly this.
- **`n_null` / `n_empty` / `n_nullish` are kept disjoint**: whitespace-only lands in nullish, a true `''` in empty. That is the NULL-vs-empty-vs-sentinel distinction the product sells.
- **`safeType` is a whitelist, and it is security-critical** — it is the one place a DuckDB type name is interpolated rather than bound. `_safe_type("BIGINT); DROP TABLE x; --")` must throw; `"DECIMAL(12,2)"` and `"TIMESTAMP WITH TIME ZONE"` must pass. - `topNSQL` gets the percentage denominator from `sum(count(*)) OVER ()` in the same pass — no companion count query.
- `histogramSQL` deliberately avoids `width_bucket()` (cross-version signature drift) and uses `epoch_ms()` for temporal columns.
- `uncastableSQL` emits `0 AS c{i}__bad` for text/nested/blob columns rather than skipping them, keeping the result shape uniform.
- `badRowCountSQL` counts **rows** with any bad cell; `uncastableSQL` counts **cells**. They are different numbers and both are shown.

### Task 5: Guard — the SELECT-only gate, pure half

**Ports:** `engine/core/guard.py` (109 lines) and the pure half of `engine/tests/test_guard.py`.

**Files:** Create `Sources/SiftCore/Guard.swift`, `Tests/SiftCoreTests/GuardTests.swift`.

**This task has a genuine architectural split, and it must be got right.**

`guard.py` does three things: strip comments, reject a denied leading keyword, and ask DuckDB to parse the statement (`duckdb.extract_statements`) to count statements and check the type. The third needs a **connection** in the C API — `duckdb_extract_statements(connection, …)` — which `SiftCore` cannot have.

So: **the first two stay here; the third moves to `SiftEngine` in Plan 3.** Record this in your report so Plan 3 inherits it. The C API pieces Plan 3 will need, verified present in `Sources/CDuckDB/duckdb.h`: `duckdb_extract_statements`, `duckdb_prepare_extracted_statement`, `duckdb_prepared_statement_type`, `duckdb_destroy_extracted`.

One consequence to note: the Python gets the statement type without preparing, but the C API requires `duckdb_prepare_extracted_statement` first — and prepare **fails** on `SELECT * FROM nonexistent` (a binder error) where Python would happily report `SELECT`. Plan 3 must therefore treat a prepare failure as "not a guard rejection" and let the real query path produce the error, or the guard will reject valid SQL against a table the user has not opened yet.

**Interfaces produced:** `func stripSQLComments(_:) -> String`, `func assertNoDeniedLeadingKeyword(_:) throws`, `struct SQLRejected: Error` with a user-facing `message`.

**Gotchas:**
- **`stripSQLComments` must preserve string literals.** `SELECT '-- not a comment'` survives; `SELECT "we--ird"` survives. It is hand-rolled rather than regex precisely for this. Swift string indexing makes a character-by-character scan awkward — work over `Array(sql)` or the UTF-8 view and build the result.
- The deny list exists because **DuckDB reports `PRAGMA database_list` as `StatementType.SELECT`** — a measured fact. Keep the comment; without it the list looks like belt-and-braces someone will "simplify".
- Rejection messages are **sentences**, and a Python test asserts they end with `.` and name the offending keyword. This module is explicitly "a message improver, allowed to be imperfect" — the real enforcement is the wrap.
- `test_denied`'s empty-string and comment-only cases must still reject here.
- The `DENY`/`ALLOW` case lists port as-is. Cases whose rejection depends on statement counting (`SELECT 1; DROP TABLE x`, `SELECT 1; SELECT 2`) **cannot be decided by this module** — mark them clearly as moving to Plan 3, and do not fake a pass by pattern-matching semicolons: a semicolon inside a string literal would then reject a valid query.

### Task 6: Stage — staging policy and purge selection

**Ports:** `engine/core/stage.py` (164 lines) and `engine/tests/test_stage_policy.py` (13 test functions).

**Files:** Create `Sources/SiftCore/Stage.swift`, `Tests/SiftCoreTests/StageTests.swift`.

**Interfaces produced:** `shouldStage(fmt:sizeBytes:freeBytes:threshold:) -> StageDecision`, `stagingName(_:)`, `ctasSQL(table:readExpr:)`, `swapSQL(table:) -> [String]`, `dropStagingSQL(_:)`, `selectForPurge(entries:now:budgetBytes:maxAgeDays:) -> (aged: [String], over: [String])`, `catalogDDL`, `StagedEntry`.

**Gotchas:**
- **`_human()` is a locale trap.** Python's `f"{n:,.1f}"` always uses a comma group separator and a period decimal point. `NumberFormatter` does not. Hand-roll it — Plan 1 shipped exactly this bug in `Cell.display` and it took a review round to catch. The Python tests assert on these strings.
- `ctasSQL` **deliberately does not** set `preserve_insertion_order = false` — rows would land out of order and the view→table swap would become visible as the grid reshuffling mid-scroll. Keep that comment.
- `swapSQL` returns a transaction as a list of statements; DuckDB DDL is transactional so the rename is invisible to readers.
- **`selectForPurge` runs age-out first, then the size check on the survivors**, so nothing is ever reported in both lists. Staged data is a copy of someone's data on a laptop, so it ages out on a clock as well as under size pressure — an LRU alone would keep a large feed indefinitely while the total stayed small.
- `NEVER_STAGE` is parquet/glob-parquet/delta: already columnar with statistics, and a flat copy of delta additionally freezes it at one version.
- Dates: `selectForPurge` compares `last_used` against `now - maxAgeDays`. Use `Date` arithmetic, and let the test inject `now` rather than reading the clock.

### Task 8: Snippet — copy-as-code

**Ports:** `engine/core/snippet.py` (216 lines) and `engine/tests/test_snippet.py` (11 test functions).

**Files:** Create `Sources/SiftCore/Snippet.swift`, `Tests/SiftCoreTests/SnippetTests.swift`.

**Interfaces produced:** `snippet(dialect:source:spec:cols:sqlOverride:) throws -> String` for `duckdb`, `pandas`, `polars`, `sql`.

**Gotchas — this task has the subtlest one in the plan:**
- **`_py(v)` is Python's `repr()`, and `repr` picks its quote character.** `repr("hello")` is `'hello'` (single-quoted) but `repr("O'Brien")` is `"O'Brien"` (double-quoted — Python switches to avoid escaping). A Swift port that always single-quotes and escapes would emit `'O\'Brien'`, which is valid Python but **not what the tests assert**. Implement the same rule: single quotes normally; double quotes if the string contains a single quote and no double quote; otherwise single quotes with backslash escaping.
- Everything this module emits is **generated source code a user pastes into a notebook**, so a wrong quote is a syntax error in their editor. Get it exactly right.
- `_ram_warning` fires only for row-oriented formats above 200 MB and states a real number: "pandas materializes the whole thing — budget roughly N GB of RAM." It uses `{gb:,.1f}` — another comma-grouping locale trap.
- The `duckdb` dialect rewrites `"tablename"` to the file read expression so the snippet runs standalone, and prepends `INSTALL delta; LOAD delta` (or `excel`) only for the formats that need it.
- When `sqlOverride` is set, pandas and polars emit a **note** saying they cannot express arbitrary SQL and to use the duckdb snippet. That honesty is the feature.
- Delta has no pandas reader without `deltalake`, so that branch emits a comment and a `pip install` line rather than broken code.

**Stays behind for Plan 3** (needs a connection): `sniffCsv`, `parquetFooter`, `exactCount`, `describe`, and `buildSource`. Note them in your report.

**Gotchas:**
- **`detectFormat` checks magic bytes before extensions**, because a `.csv` that is really an Excel file — or an HTML error page saved with the wrong name — is a genuinely common way to receive data. `PAR1`, `\xd0\xcf\x11\xe0` (OLE2 → legacy `.xls` refusal), `PK\x03\x04` (zip → xlsx or refuse).
- **`isDeltaDir` exists because globbing a Delta table's parquet files is *wrong*.** The log's `remove` actions tombstone files that are still present, so a raw glob resurrects deleted rows. Measured on a two-version fixture: raw glob 150 rows, `delta_scan` 100. Keep the comment — that failure looks like a data bug, not a tool bug.
- **`globEscape`** escapes `[`, `]`, `*`, `?` in a literal directory path — a folder named `data[2026]` would otherwise be read as a character class and silently match nothing.
- **`hiveKeys` returns keys only if EVERY file carries the identical key set**, because DuckDB errors on `hive_partitioning := true` for an inconsistent layout.
- **`estimateRows` samples three windows** and extrapolates, because an exact `count(*)` on a multi-GB CSV is a full parallel parse. Confidence is `low` whenever any quote character appears in the sample: a quoted field containing a newline makes line-counting overshoot and there is no cheap way to know how often. Use `FileHandle` for the seeks. Preserve the exact `basis` strings — the UI shows them on hover and the tests assert them.
- **`XLSXSheets` replaces openpyxl.** An `.xlsx` is a zip. Run `/usr/bin/unzip -p <file> xl/workbook.xml` via `Process` for sheet names and order, then `xl/worksheets/sheetN.xml` for each `<dimension ref="A1:F1000"/>`. **Parse with `XMLParser`, never a regex** — a sheet named `R&D` arrives as `R&amp;D` and a regex silently mangles it, while an apostrophe (`it's a sheet`) arrives unescaped inside a double-quoted attribute. Both fixtures are committed; the README explains why.
- A workbook with no `<dimension>` reports `rows: 0, cols: 0` and is treated as **non-empty**, so the picker still offers it rather than hiding it.
- `readExpr` bakes options in explicitly rather than relying on `read_csv_auto`, so no later query re-sniffs the file — the single largest first-paint win for CSV.
- **🔴 The CSV `columns=` argument must be built from `SourceSpec.columns`, never from a dictionary.**
  Python sets `read_args["columns"] = {c.name: c.type for c in cols}` in file-column order and
  renders it via `.items()`, relying on dicts being insertion-ordered. `read_csv(columns={...})`
  **disables auto-detection and binds by position** against the file, so the order is a correctness
  dependency. A Swift `Dictionary` is unordered — rendering one silently assigns the wrong type to
  each column, which is a plausible-wrong-value bug in the one product that exists to not produce
  those. `SourceSpec.columns` is already an ordered `[Column]` holding exactly those (name, type)
  pairs: derive the argument from it, and do not add a `columns` case to `ReadArg`.
- `readExprAt` is Delta time travel: `version => n` works, `AT (VERSION => n)` does not parse.
